# Session 041 — 2026-03-11

## What Happened

Implemented Phase 9: Action Pipeline. Built thin authorization middleware (`src/core/action-pipeline/index.ts`) that wires Gate 1 (Task Engine `checkPermission`) → Gate 2 (Safety Layer `evaluateAction`) → Execute → Notify. Options object input pattern (`ExecuteInput<T>`), discriminated union return (`PipelineResult<T>` with 4 outcomes), async from the start. Read actions skip Gate 2. First use of `vi.fn()` mocks in the project. 20 new tests, 850 total. All verification passes.

## Decisions Made

1. **Options object for `execute()` input** — `ExecuteInput<T>` with named fields (`taskId`, `actionClass`, `details`, `requestedBy`, `executeFn`, `notifyFn?`). Matches `CreateTaskInput` pattern. Cleaner than 6 positional args.

2. **Discriminated union return type** — `PipelineResult<T>` with `outcome` discriminant: `"executed"` (success + result), `"rejected"` (gate + reason), `"ask_human"` (reason + warnings), `"error"` (reason + error). Four distinct outcomes, not boolean.

3. **Pipeline enforces read-only Gate 2 skip** — `actionClass === "read"` skips `evaluateAction()` inside the pipeline. Callers don't need to know the rule.

4. **Async from the start** — `execute()` returns `Promise<PipelineResult<T>>`. Gates are sync (in-process DB), but `executeFn` can be async. Avoids breaking change when Phase 10/11 need async execution.
