## Decisions Made

1. **Extract a shared `cancelTask` helper** (Q&A-confirmed) over inlining the guarded write twice. The
   `version`-bump that protects the cross-process race is correctness-critical; a single source (used by the
   dashboard endpoint and the CLI) keeps it from drifting out of one copy, and the race test targets one
   function. Lives in `core/task-engine/cancel.ts`, barrel-exported; both callers are thin shells mapping its
   discriminated result to HTTP status / CLI exit code.
2. **`user_cancelled` is handled outside `handleTerminatedOutcome`** (refinement found during grounding).
   It is already terminal — it does not route to a recovery state — so it does not belong in the routing
   surface. `handleTerminatedOutcome`'s `reason` param is narrowed to `Exclude<…,"user_cancelled">` (the
   compiler enforces the separation), and `handleTaskCompletion` dispatches `user_cancelled` to a dedicated
   `handleUserCancelledTermination`. This was also what kept both functions under the complexity ceiling.
3. **Keep `closePR`-on-cancel (D12)** (Q&A-confirmed) — the surface turned out small (`closePR` +
   `commentOnPR` + `getPRStatus` all existed, the fake implements them, the all-or-nothing envelope was
   already there to mirror), and it is the clean abandon semantic (no orphaned PR). S3 did not run hot, so the
   "first to cut" flag was never exercised.
4. **Active-only `ticket_comment` this session** (Q&A-confirmed). The daemon (the only process that can reach
   the comm plugin) emits the cancel comment from `handleUserCancelledTermination`, which fires once when the
   aborted dispatch settles — naturally once-only and symmetric with the completion comment. Non-active
   cancels (queued / requirements_gathering / blocked-not-on-PR) get no source-ticket comment yet; that
   broader coverage is notification policy → Slice 10.
5. **The `closePR` contract case asserts "resolves without throwing"**, not a stateful close→closed round-trip
   — the github plugin's test mock is non-stateful, so the stronger assertion is plugin-specific (the github
   test already verifies `pulls.update({state:"closed"})`; the reaper test verifies the call sequence).

- The dashboard cancel was transitioning to `failed`, not `cancelled` (its existing test asserted `failed`).

  plan's "Where" did not list).
