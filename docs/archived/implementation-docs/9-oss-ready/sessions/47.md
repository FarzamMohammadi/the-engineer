## What Happened

The merge loop is now end to end. A green PR earns `pr_ready_to_merge` (a formal approval, or an
authorized `/approve` the poller live-confirms is green + mergeable) → the poller writes the event type
and re-queues → the orchestrator re-enters at `delivery/auto-merge` via `entryFor` → auto-merge re-checks
the live PR, removes branch thoughts (if configured), merges with the configured strategy, deletes the
remote branch, and emits the merge audit events → the task completes; the scheduler reaps the worktree.

1. **`d774178` Fill auto-merge with the live safety-gated merge and audit events.** `auto-merge.ts`'s
   shell became the live body: `run` re-derives readiness from `getPRStatus` (already-merged → done;
   `checkAutoMergeAllowed` false → complete for a manual merge; CI failing → `ci_failure`; not mergeable →
   `merge_conflict`; checks not yet passing → `retry_wait`; green + mergeable → `removeThoughtsAndPush`
   if `exclude_thoughts_on_merge`, then `mergePR`), and `next` routes purely on the disposition
   (merged/disabled → done; ci_failure/merge_conflict → `jump` to execution; retry_wait →
   `block(awaiting_pr_review)`). A successful merge records `review.pr_state = "merged"`, publishes
   `git.pr_merged`, and deletes the remote branch (when `delete_branch_after_merge`) with
   `git.branch_deleted`. Both events' publisher moved from the daemon (whose review-handler publisher 7a
   deleted) onto the **orchestrator**. The merge-specific cleanup (remove-thoughts, remote-branch delete)
   lives in auto-merge; the generic worktree reap stays in the scheduler's completion path (locked in 7a).
2. **`8a7286a` Route merge PR events to auto-merge and promote a green approve.** The poller stopped
   dropping `pr_ready_to_merge`/`pr_merged` with a debug log; both now re-enter via the same
   write-event-and-re-queue path the rework events use. An authorized `/approve` (the single-contributor
   approval path) promotes to `pr_ready_to_merge` — and drops the same-poll comments — only when
   `enable_comment_approval` is on **and** a live `getPRStatus` confirms open + green + mergeable; a
   not-yet-green `/approve` keeps the task waiting, while a same-poll CI failure / conflict still routes
   the real rework. Re-wires `enable_comment_approval`, which had no caller after 7a deleted the
   review-handler.
3. **`16f73fe` Guard the blocked consumers so a comment never unblocks a review-pending task.**

## Decisions Made

All four surfaced to Farzam up front; he took every recommendation.

1. **The `/approve` green/mergeable re-check happens in the poller, before writing the event** (not inside
   auto-merge). Keeps `pr_ready_to_merge` honest — it always means "merge now" — and a pending-CI
   `/approve` never gets bounced into a needless re-review. auto-merge still does a final defensive
   re-check for the rare tick-gap race.
2. **A merge failure splits by cause.** A *definitive* CI-failure / conflict → in-dispatch `jump` to
   execution, counted by `total_reworks` (D12); the rework dismisses the approval (via create-pr's rework
   path), so a human must re-approve before the next merge — that human gate is what bounds the loop. A
   *transient* miss (pending checks, a flaky merge API, a non-conflict rejection) → `block(awaiting_pr_review)`
   so the stateless poller retries when the PR is ready again, with no wasted rework.
3. **The consumer guard is both layers, with distinct roles.** `unblock-resolver` is the authoritative
   rule (covers every caller incl. the dashboard/event-bus path); `response-poller`'s scoping is
   input-narrowing (don't even consider review-pending tasks for the sole-blocked fallback or channel
   polling). The dashboard path reaches the resolver directly, so the resolver guard is essential, not
   redundant.
4. **Re-wire `enable_comment_approval`.** It went dead when 7a deleted the review-handler. The
   `/approve`→merge promotion is gated on it (default off → `/approve` never triggers a merge; the
   operator does a formal approval). The strict `^/approve(d)?$` regex means a mixed comment still reworks.

## Known Edge / Limitation

**A narrow merge-retry loop.** If a PR is genuinely approved + green + mergeable but `mergePR` keeps
failing for a *non-conflict* reason (e.g. a required check the merge API enforces but `getPRStatus`
reports as passing), the poller re-queues each daemon tick and `auto-merge` posts a "merging" ticket
notice each time → `retry_wait` → wait → repeat. This is **bounded by the poll cadence, self-heals for
real transients, and matches the legacy review-handler's unbounded "retry next tick."** It is *not* a
regression. The pending-CI case does **not** loop (the plugin only emits `pr_ready_to_merge` when
checks are passing, so a pending PR simply waits). A clean future hardening, if it ever bites: a
persisted merge-attempt counter that fails the task to the operator after N attempts (kept out of 7b to
avoid speculative state, per YAGNI). Flagged to Farzam; left as-is for now.
