## Decisions Made

1. **Trivial-complexity flows via the file handoff** *(Farzam's pick)*. `research`/`planning` `skip(ctx)` read complexity from `requirements/session-result.json`'s `details` (the same file-based handoff the architecture already uses) — no schema/DB/Ctx change, crash-safe, dark-friendly. The task-row mirror is an S5-cutover option if the dashboard wants to query it.
2. **Grounding is the foundational first step** *(Farzam's steer — I had over-framed "where do verify's gates come from" as an isolated design fork)*. The agent acclimates to the project the way a real engineer joining it does, and the verification commands fall out of that grounding (recorded in requirements' `details`), not a bolt-on detector. Split discovery (judgment, agent) from the verdict (orchestrator-owned, unfakeable): `verify` runs the recorded commands itself. Captured as `feedback_grounding_first` + `reference_dev_toolbox_rrpir_skills` memories; the dev-toolbox rrpir skills are the prompt-refinement reference for this slice.
3. **Trivial skips both research AND planning** (slice-locked behavior change; legacy skipped research only).
4. **New prompts are preview** — grounding / context-summary-first / observations-vs-inferences / design-and-stress-test disciplines woven in now; the exhaustive dev-toolbox port stays Session 8. A compact new system prompt was written for the dark pipeline (bounded duplication with the legacy `system.ts` until the S5 cutover deletes legacy).
5. **A `pipeline.test.ts` pins the phase-map shape** — guards the heart-of-the-system artifact and lets the sub-phase commit stand green on its own (the integration test is the runtime guard; this is the structural one).
