# Session 013 — 2026-03-08

## What Happened

Began Layer 3 (Interactions & Protocols). Planned the full Layer 3 structure: 5 docs, one per session, two-pass approach for plugin contracts. Discovered a timing ambiguity in the Layer 2 Event Bus pre-processing model (events named in past tense but intercepted pre-action). Resolved it with a major architectural refinement: the Action Pipeline, derived from auth middleware systems (HTTP middleware, Kubernetes admission controllers, Linux DAC+LSM). Drafted the complete Event Catalog — 26 event types across 9 groups, all formalized with schemas, owners, and subscriber tables.

## Decisions Made

1. **Action Pipeline replaces Event Bus pre-processing (Decision #42)** — Derived from auth middleware systems. Safety checks happen in a middleware chain (Gate 1: Task Engine state check → Gate 2: Safety Layer policy check) BEFORE action execution. Event Bus becomes pure pub/sub for post-action notifications. No more synchronous interception, no timing ambiguity. Defense-in-depth = two pipeline gates, both must pass.
2. **Layer 3 document structure: 5 docs** — event-catalog.md, plugin-contracts.md, protocols.md, error-propagation.md, lifecycle.md. Error propagation stays separate (not merged into protocols).
3. **Two-pass approach for plugin contracts** — Draft contracts before protocols, finalize after protocols surface missing requirements.
4. **`action.requested` removed, `action.rejected` added** — No pre-action events needed (pipeline handles checks). Only rejections logged as events (successful actions have their own specific post-action events).
5. **Orchestrator receives events via Daemon, not direct Event Bus subscription** — Simplifies subscription lifecycle management.
