# Session 070 — 2026-03-22

## What Happened

Continued RRPIR implementation. Wired planning + execution handlers to CLI-native invocation (4/7 phases now use runPhaseWithCli). Built universal fallback routing so any phase can signal need_more_info and loop through requirements_gathering, then return to the exact calling phase. Implemented external blocking with persistent return_to_phase (DB migration 007) for when requirements_gathering needs human input. Added crash recovery detection via session-result.json state. Key design decision: session-result.json stays pure routing (status, next_phase, summary); all rich context lives in .md deliverable files. Decomposition from plan.md deferred. Post-commit triple review (simplify + persona + PR reviewer) caught 7 issues — refinement pass applied (PhaseSchema validation, state mutation safety, test deduplication).

## Decisions Made

1. **Separation of concerns: routing vs. content** — session-result.json is pure state routing (3 fields). All rich context (ambiguities, questions, findings) lives in .md deliverable files. Only requirements_gathering talks to people via People Directory.
2. **return_to_phase as top-level DB column** — not inside blocked JSON. Exists independently of blocked state, easier to query/filter. Migration 007.
3. **Decomposition from plan.md deferred** — edge case for now. Documented migration path in future-considerations.md.
4. **Crash recovery via session-result.json** — if the file already has values (not placeholders), this is a resumed session. Re-evaluate plan.md and codebase state rather than blindly skipping checked boxes.
5. **Status-only routing** — removed redundant `|| next_phase === "requirements_gathering"` condition. `need_more_info` status is the sole fallback signal.
