# Session 073 — 2026-03-23

## What Happened

Extracted UnblockResolver as a shared Core abstraction (two lookup paths: by external_ref, by task_id), wired comm.message_sent event publishing in both outreach and notification flows, built dashboard response API (POST writes comm.message_received to events table, daemon polls and calls resolver). Parallel session completed dashboard comm research doc. Triple review (persona + architect) revealed a critical architectural flaw: auto-unblocking was wired through the trigger poller, conflating intake (new work) with communication (responses). Designed the proper fix: a `response-poller.ts` daemon subsystem using CommunicationAdapter's `receive` capability with `pollMessages()`. Plan approved for next session.

## Decisions Made

1. **Triggers = intake, communication = conversations** — auto-unblocking must flow through CommunicationAdapter `receive`, not through the trigger poller. Different concerns, different subsystems.
2. **No dashboard comm plugin** — the dashboard reads/writes events from SQLite. It's an event consumer/producer, not a comm plugin. Eliminates fake boilerplate.
3. **Reuse `comm.message_received`** — no new event types. Existing schema has source, sender, content, task_id.
4. **Response content written to worktree** — `thoughts/{id}/requirements/responses/{source}.txt` so requirements_gathering reads it on resume. File-based handoff, consistent with RRPIR.
5. **Remove trigger poller unblock check** — conceptually wrong (triggers aren't responses) AND practically broken (dedup runs before unblock check, so comments on seen issues get filtered out).
6. **`CommunicationAdapter.pollMessages(channels, since)`** — new optional method under `receive` capability. Plugin fetches comments for specific conversations. Response poller builds channel list from blocked tasks.
