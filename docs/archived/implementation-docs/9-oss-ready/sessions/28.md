## Decisions Made

1. **Test-daemon mock subscriptions keyed by subscriberId, not eventType.**
   The mock previously used `subscriptions.set(eventType, callback)`, which
   broke as soon as `health.stuck_detected` got a second subscriber
   (`daemon:hard-cap` clobbered `daemon:health-stuck`). Switched to a
   `Map<subscriberId, {eventType, callback}>` keyed by subscriber ID.
   `getSubscriptionCallback(key)` now tries subscriber ID first, then falls
   back to first-match by event type — so the existing 13 callers that look
   up by `EventTypes["foo"]` keep working unchanged, and new tests can
   disambiguate via the subscriber ID directly. Cleaner than asking every
   existing caller to migrate.

2. **Threshold inlined in the hard-cap alert.** The Session 3 alert said
   "exceeded the maximum active duration" without naming the actual cap. The
   plan's wording included `{threshold} minutes`. Pulled `config.max_active_duration_ms`
   (already in scheduler scope) and rendered it as
   `${Math.round(config.max_active_duration_ms / 60_000)} minutes` so the
   owner sees the real number ("exceeded 480 minutes of total active time")
   rather than abstract jargon. Universal-audience win.

3. **`engineer retry` transaction body split into named helpers.** Adding the
   second retryable state (`failed`) and the second counter reset tipped the
   transaction's cognitive complexity from 14 → 17, over the 15 ceiling.
   Split: `clearBlockedPreservingContacts` (the conditional reason/needed/
   contacted reset) and `extractContactedHistory` (the try/parse helper). The
   transaction now reads top-down as the sequence it is: insert state
   transition → state update → conditional blocked preservation → counter
   reset. Newspaper order — caller above callees.

4. **Terminal-states test split rather than weakened.** The pre-existing
   assertion "terminal states (completed, failed) are never a 'from' state"
   needed updating for the `failed → queued` edge. Rather than changing the
   set to `{completed}` only, split into two tests: `completed` keeps the
   strict no-from invariant, `failed` gets a *positive* assertion that it has
   exactly one outgoing edge to `queued`. The new test will catch a future
   accidental `failed → active` edge — the kind of regression a weakened
   assertion would silently allow.

5. **State-machine **States** table left for Session 5.** `overview.md`'s
   States table still lists `supervising` / `integrating` as `active`
   sub-states (stale post-Session-1 decomposition delete). Only the mermaid
   diagram was touched this session (added `failed → queued` edge). The
   table is a multi-row edit that belongs in the closing-sweep audit, not
   bolted onto a tie-up session.
