Combined total: 412 tests across 10 test files.

## Decisions Made

1. **`DatabaseHandle { db, close() }` wrapper**: Thin wrapper instead of raw `better-sqlite3.Database`. Gives consumers full `db` access for `prepare()`, `transaction()`, etc., with `close()` for lifecycle management. Not a deep abstraction — just enough for cleanup.
2. **No prepared statement helpers**: Consuming phases (Event Bus, Task Engine, etc.) define their own domain-specific queries. No premature abstraction at the DB layer.
3. **`_meta` owned by migration runner**: Runner bootstraps `_meta` with `CREATE TABLE IF NOT EXISTS` and seeds `schema_version = '0'` before reading version. `001_initial.sql` contains only the 7 domain tables + indexes. Clean separation.
4. **Migration file resolution via `import.meta.dirname`**: Node 22+ ESM-native, already used elsewhere in codebase. Production build copy deferred to Phase 12/13.
5. **WAL mode after migrations**: Per sqlite.md startup flow. Skipped for `:memory:` databases (not supported).
6. **Two separate functions**: `createDatabase()` and `createInMemoryDatabase()` instead of one with optional path. Different behavior (WAL, file creation) warrants separate APIs.
