## Decisions Made

1. **Plugin reports facts, Core owns policy** *(Farzam-aligned, D8-faithful)*. The plugin's
   `pr_ready_to_merge` is formal approval + CI-green + mergeable; `/approve` recognition and authorization
   live in Core, so a new hosting plugin never learns The Engineer's `/approve` convention or touches the
   people-directory. Chosen over folding `/approve` into the plugin, which would duplicate the convention
   across every future plugin (against the plugin-interchangeability moat).
2. **`/approve` is a real approval path equal to a formal approval** *(Farzam's steer)*. A sole contributor
   can't self-approve their own PR on the host, so `/approve` (and `/approved`) counts. **Authorization is
   permissive when no people are configured** (the solo case just works) **but gated once an owner/reviewer
   is** — a drive-by `/approve` on a public repo never merges (Trust Through Restraint floor). The
   owner-only tightening is a documented future knob. Captured in `constraints.md`.
3. **Thin, fetch-don't-store payloads** *(Farzam's steer)*. Only `pr_comments` carries data; the agent
   pulls richer platform detail live via the plugin on re-entry rather than persisting it on the task row.
4. **`entryFor`/`arbitrate` moved into a new `pipeline/pr-events.ts`** with the new helpers — one cohesive
   PR-event Core policy module; `pipeline.ts` stays the map.
