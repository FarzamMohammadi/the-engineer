# Session 074 — 2026-03-23

## What Happened

Implemented the response poller subsystem — proper separation of triggers (intake) from communication (responses). Added `pollMessages()` to CommunicationAdapter contract, implemented `doPollMessages()` in GitHubCommPlugin (issue comment polling with self-comment filtering), created `response-poller.ts` daemon subsystem, wired into tick loop, and removed the unblock check from the trigger poller. Then ran a triple review (Engineer persona, Technical Architect, QA Integration Tester) of the entire blocked/unblock communication flow. Reviews found 3 bugs: historical comment replay on first poll (HIGH), event bus replay on restart (MEDIUM), spurious query handler responses (MEDIUM). All 3 fixed. 2,322 tests passing.

## Decisions Made

1. **Triggers = intake, communication = conversations** — trigger poller no longer participates in unblocking. Response poller owns all response detection.
2. **CommunicationAdapter.pollMessages(channels, since)** — new optional method under `receive` capability. Channel format is `"owner/repo#42"` — plugin-specific parsing.
3. **Default cursor to current timestamp** — first poll skips historical comments. Prevents stale comments from triggering false unblocks.
4. **Initialize lastEventSeq to max sequence** — skip historical events on startup/restart. Prevents re-unblocking with stale dashboard responses.
5. **Skip task-directed events in QueryHandler** — messages with `task_id` are for unblocking, not queries. Prevents spurious "I didn't understand" responses.
6. **No dashboard comm plugin needed** — dashboard reads/writes events from SQLite. It's an event consumer/producer, not a comm plugin.
