# Session 005 -- 2026-03-07

## What Happened

Farzam proposed an intermediary phase before Layer 2: design concrete user flows to validate Layer 1 from the user's experience, not just the architect's. Major design discovery: two-stage PR review with demo gate.

## Decisions Made

1. **Layer 1.5: User flows before component design** -- validate Layer 1 from the human's perspective before drilling into component internals. Catches experiential gaps that component simulation misses.
2. **Two-stage PR review (Demo Gate)** -- Draft PR = demo gate ("did you build the right thing?"), Ready PR = code review ("did you build it right?"). Feedback applies at both stages. Everything is demo-able — backend gets temporary TUI for demos.
3. **Communication channels: GitHub + Telegram** -- GitHub for code workflow, Telegram bot for real-time comms. Both free, both accessible. All channels are plugins.
4. **Real engineer judgment over prescribed policies** -- no hardcoded policies for demo rejection, conflicting reviews, feedback severity. The Engineer uses judgment. The architecture enables any response; it doesn't prescribe one.
5. **Auto-merge configurable per repo** -- default: wait for owner to merge manually.
6. **Conflicting reviewer feedback** -- Engineer facilitates consensus in the PR thread like a real engineer, not escalate-and-wait.
7. **Proactive updates: milestone-based + optional daily digest** -- configurable.
8. **State machine as security boundary** -- each state defines what actions are LEGAL. Phase determines permissions. Defense in depth on top of Safety Layer. The state machine is a failsafe — even if the LLM hallucinates, structurally impossible actions are blocked.
9. **Phase loopback as formal state transition** -- Orchestrator decides to loop back, Task Engine enforces it. Permission set resets. Audit trail records the transition.
10. **DevEx for the Engineer** -- invest in the Engineer's tooling. First instance: base TUI project for backend demos (Engineer extends it per-task in isolated worktrees). Pattern extends to any tooling that makes the Engineer more effective.

## Flows Designed

1. Task Assignment → Delivery (happy path)
2. Mid-Task Interaction (Blocked ↔ Active)
3. Review Feedback Loop (Draft + Ready, two-stage)
4. Monitoring & Observability (status queries)
5. Self-Decomposition (user's view of task breakdown)
