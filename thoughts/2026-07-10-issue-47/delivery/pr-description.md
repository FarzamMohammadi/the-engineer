## What & why

When a PR was approved through The Engineer's `/approve` comment convention but the git host's **branch protection** refused the merge (GitHub reports `MERGEABLE` yet `mergeStateStatus: BLOCKED` / `reviewDecision: REVIEW_REQUIRED` — it wants a *formal* review a comment cannot provide), the engine fell into an **infinite rework loop**: the poller re-promoted the same `/approve` to `pr_ready_to_merge` every poll → auto-merge attempted the merge → the host refused → the failure routed into `execution/implement` for a full rework cycle → the re-push re-blocked at await-review → the poller saw the same `/approve` again → forever. Each lap burned an agent cycle, re-pushed the branch, and climbed the cost with nothing to stop it (`max_blocker_reentries` does not classify `pr_ready_to_merge` as a blocker, so the cap never applied). It only ended when the owner force-merged.

This change establishes one rule and one contract: **a merge the host will not complete never drives rework.** It is handed off to the owner — resumably, with an honest message — and both code paths that can detect it resolve to the identical state.

## How

Three conflations, fixed at their sources across the plugin → contract → Core boundary:

- **The contract can now say "blocked."** `PRStatus.merge_state` was `mergeable | conflicting | unknown` — it had no way to express *"mergeable in shape, but the host will not merge it."* Added `blocked`, host-agnostic and distinct from `conflicting` (a textual conflict, which still *does* rework).

- **The GitHub plugin reads the host's real signal, via an allowlist.** `mapMergeState` now consults `mergeable_state` alongside the boolean `mergeable`. Order matters: `null → unknown`, `false → conflicting`, then `mergeable_state` decides — `clean`/`unstable`/`has_hooks`/`behind` → `mergeable`; everything else (`blocked`, `draft`, any state GitHub adds later) → `blocked`. Deliberately an **allowlist**, not a `"blocked"`-only denylist: a merge attempt is not free (it first pushes a thoughts-cleanup commit, which can dismiss a formal approval and re-push the branch), so an unrecognized state must hand off rather than gamble on a merge. The `mergeable_state` check runs *before* collapsing `mergeable === true`, because a blocked PR still reports `mergeable === true`. Host-specific detection stays entirely inside the plugin; Core switches only on the contract string, so a second hosting plugin inherits the safety by returning `blocked`.

- **One shared contract, both paths — `orchestrator/pipeline/host-blocked-merge.ts`.** The condition is reachable from two places, and they used to resolve it *contradictorily* (one blocked-resumable promising "I'll merge it", the other done-terminal saying "you merge it"). Both now import a single block category and a single owner-facing message:
  - **Auto-merge** diverts `blocked` in `decideReadiness`, *before* any `mergePR` call — no doomed attempt, no cleanup re-push, no rework. Its merge-failure backstop (the narrow detect→merge race) resolves to the same hand-off. It routes `go: "block"`, **not `done`** — completing the task would post "Task completed successfully." on an *unmerged* PR, destroy the worktree, and make impossible the very retry the message asks for.
  - **The poller** no longer re-promotes: `shouldPromoteApproval` became `resolveApproveDisposition` (`promote | escalate_blocked | wait`). A green-but-`blocked` `/approve` escalates on the same contract. The `blocked` check is gated on `checks_state === "passing"`, symmetric with `promote`, so a red-CI blocked PR still takes the normal CI-rework path.

- **The loop is structurally bounded, not counted.** The shared category is `awaiting_human`, which `toBlockReason` collapses to `need_more_info` — taking the task **off** the `pr_review_pending` poll set entirely, so the promote → doomed-merge → rework cycle cannot re-form, and onto the blocked-escalation ladder (nudge → self-unblock → honest `failed`, never a false `completed`). That mapping is load-bearing for loop safety, so `toBlockReason` is now exported and asserted directly rather than assumed.

- **The message is honest in both worlds.** `mergeable_state === "blocked"` cannot distinguish "a required review the owner *can* add" (the Engineer merges on retry) from "the Engineer has no merge permission" (only the owner ever can). Rather than pay a GraphQL `reviewDecision` call to guess — and risk a confidently wrong promise — the wording holds either way: *approve on the host, then `engineer retry` — I'll merge it **if the host lets me**; if it still refuses, merge it yourself.* It never promises an unconditional "I'll merge it."

**Unchanged on purpose:** an approved + green + host-will-merge PR still merges automatically, and a genuine conflict (`mergeable === false`, or a 409 from the merge call) still routes to `execution` rework.

## Verification

- **Gates green on the final tree:** `typecheck` PASS · `lint` PASS (biome + tsc + tsc-test + knip + madge, no circular deps) · `test:unit` **2837 passed** · `test:integration` **67** · `test:e2e` **16**.
- **Tests at every seam:** poller escalation + the loop bound; auto-merge blocked hand-off (asserting `mergePR` is *never called*) and its failure-path backstop; plugin `mergeable_state` mapping (allowlisted, `blocked`, `draft`); `derivePrEvents` withholding `pr_ready_to_merge` / `pr_merge_conflict` for a blocked PR.
- **A coherence regression test** (`tests/unit/core/host-blocked-merge-contract.test.ts`) proves both paths land in the *same* lifecycle state with the *same* message for the same host-blocked condition, and that `toBlockReason(awaiting_human)` is `need_more_info` and **not** `pr_review_pending` — the assertion that keeps the auto-merge path off the poll set.
- **The two loop-bound guards were mutation-tested**, not merely run green: deleting the poller's `escalate_blocked` disposition, and re-mapping `awaiting_human → pr_review_pending`, each now **fail** the suite. Both previously passed — one of the two tests was vacuous (it stubbed an empty poll set, so `poll()` returned before reaching any escalation code) and was rewritten to derive its poll set from what the escalation actually writes.
- **Worth a reviewer's eye:** the ordering inside `mapMergeState`, and the `checks_state === "passing"` gate on the escalation.

## Risks & follow-ups

- **The hand-off message names branch protection, but `mergeable_state: "blocked"` is a catch-all.** With the allowlist, a `draft` PR (or a future GitHub state) also maps to `blocked` and would receive a message about a formal review. The **routing is correct and safe in every case** (hand off, never rework, never loop, stays resumable) and the promise stays honest — only the diagnosed *cause* can be imprecise on a rare state the Engineer never creates itself. Diagnosing every `mergeable_state` precisely would widen the contract beyond what this issue asked for.
- **`behind` is allowlisted → `mergeable`.** If protection requires an up-to-date branch the host refuses, answering **405**, which the failure classifier maps to `not_mergeable` → the same shared hand-off. Verified this cannot loop; excluding `behind` outright would stall PRs the host would happily merge.
- **A *formally*-approved-but-blocked PR still waits silently** rather than escalating — it emits no event and no `/approve`. Correct per the requirement ("waits … or escalates"), pre-existing, and outside this ticket's `/approve`-comment scope.
- **Out of scope:** the CI non-final / re-running-checks debounce — sibling issue **#46**, which lives in different code and lands separately.
- **This PR will demonstrate its own fix.** It is itself `MERGEABLE` + `BLOCKED` + `REVIEW_REQUIRED`, so it needs a **formal GitHub review approval** — a `/approve` comment cannot satisfy it. That the Engineer hands it off instead of looping is the expected behavior after this change, not a failure.
