## Decisions Made

1. **Phase-runner does NOT call retry-policy.** The plan literally said both T2.4
   (scheduler `handleLlmUnavailableBlocked`) AND T2.5 (phase-runner `LlmUnavailableError`
   catch) would call `recordFailure("llm_unavailable", ...)` — which double-increments
   the counter on every LLM-unavailable event. Resolved by making the scheduler the
   sole `recordFailure` caller for `llm_unavailable`. Phase-runner just blocks the task
   with the error context and returns `Outcomes.blocked`; scheduler owns the
   disposition-aware notification (retry-with-minutes vs. terminal-await-owner) and the
   re-queue decision. Bonus: phase-runner imports nothing from retry-policy, so the
   cross-boundary import smell is closed from both directions.

2. **Per-outcome `recordSuccess` semantics.** Old code unconditionally reset
   `consecutive_crash_count` (which was also the LLM retry counter in the shared-field
   design) at the top of `handleTaskCompletion` — silently clobbering phase-runner's
   increment and preventing the LLM retry budget from ever exhausting. New code: reset
   both counters on non-blocked outcomes; on `Outcomes.blocked`, reset only the crash
   counter (this wasn't a crash) and let `handleLlmUnavailableBlocked` own the
   llm_unavailable counter via `recordFailure`. Per-category fields make this honest.

3. **Boot recovery is a real failure event.** `rebuildStateFromTaskEngine` now routes
   each orphaned active task through `retryPolicy.recordFailure("crash")`. If the
   policy returns terminal (budget exhausted), the task transitions straight to
   `failed` instead of `queued` — closing the boot-loop hole where a
   systemd-restarted daemon could re-pick up a guaranteed-to-crash task forever.
   E2E test had to advance the fake clock past the first-crash backoff (1 minute)
   because recovery now applies real backoff.
