# Session 30 — 2026-03-10 — Layer 5: Build Order Planning

## What Happened

Designed the implementation build order for Layer 5 — the sequence of coding sessions that will turn 127 architectural decisions into a working system. No code written; this session produces the blueprint.

## Approach

Bottom-up, like a compiler bootstrap. Schemas and infrastructure first, then components in dependency order, then the daemon that wires everything together. Each phase builds on the last, nothing reaches backward.

Read all Layer 4 specs (foundation, layout, schemas, plugins, operations, testing), architecture docs (overview, tiers, lifecycle), and the holistic review (Session 29) to map the full dependency graph.

## Key Design Decisions

### Build Order Structure (Decision #128)

16 phases, bottom-up:

| Phase | Name | Scope |
|-------|------|-------|
| 0 | Project Bootstrap | Small |
| 1 | Zod Schemas | Large |
| 2 | Database Layer | Small |
| 3 | Config System | Medium |
| 4 | Event Bus | Medium |
| 5 | Adapter Base Classes + SDK | Small |
| 6 | Registry + Fake Plugins + Test Infra | Large |
| 7 | Task Engine | Medium |
| 8 | Safety Layer + People Directory | Medium |
| 9 | Action Pipeline | Small |
| 10 | Session/Memory + Workspace Manager | Large |
| 11 | Orchestrator (Skeleton) | Large |
| 12 | Daemon + Logging (HELLO WORLD) | Large |
| 13 | CLI | Medium |
| 14 | v1 Plugin Implementations | Large |
| 15 | Integration + E2E Tests | Large |

### Resolved Sub-Decisions

- **Schema scope:** Keep as one phase — pure data with no runtime deps, avoids context-switching between sessions.
- **Plugin timing:** Build plugins last — fake plugins sufficient for core testing. Real plugins add distracting external API complexity (GitHub, Telegram, etc.).
- **Hello world timing:** Phase 12 is natural. Bottom-up means each phase is independently testable via unit tests. A premature daemon skeleton would just be a stub.
- **Phase granularity:** Keep "Large" phases as-is (7 of 16). Can split during execution if any proves too big.

### Dependency Cycle Resolution

The chicken-and-egg is broken by build order:
- Action Pipeline (Phase 9) needs Task Engine (Phase 7) and Safety Layer (Phase 8) — both built first
- Orchestrator (Phase 11) needs Action Pipeline + Registry + everything — all exist by then
- Daemon (Phase 12) is the final wiring point — everything ready

### Parallelization Opportunities

- Phases 2 + 3 can run in parallel (both depend only on 0 + 1)
- Phase 14 (plugins) can run in parallel with Phases 6-13 (only depends on Phase 5)
- Unit tests co-located with each phase — no separate "test writing" sessions

## Decisions Made

| # | Decision | Rationale |
|---|----------|-----------|
| 128 | 16-phase bottom-up build order | Dependencies flow forward. Each phase testable independently. Hello world at Phase 12 when full stack is wired. Schemas first (everything depends on types), infrastructure next (DB, config, Event Bus), then components in dependency order, then daemon/CLI, then real plugins, then integration/e2e tests. |
