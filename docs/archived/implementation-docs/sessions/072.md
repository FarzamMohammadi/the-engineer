Separately, guided a parallel session designing the Dashboard Communication Plugin. Key architectural decisions through Q&A: plugin is dumb transport (no DB access), receive path goes through Core not plugin, and — most importantly — proposed a shared **UnblockResolver** in Core that any source feeds into (trigger poller, dashboard API, future Telegram/Slack receive). Eliminates source-specific unblock paths. Research doc being written by parallel session.

## Decisions Made

1. **`blocked → queued` transition** — unblocked tasks go through the scheduler (respects concurrency slots) rather than jumping to active directly.
2. **Match on repo + number only** — `externalRefsMatch()` ignores `type` field. GitHub's shared issue/PR number sequence makes this safe and technology-agnostic.
3. **Clear blocked field after transition, not before** — prevents losing blocking context (reason, efforts_made) if the transition fails. Caught by triple review.
4. **Dashboard Comm Plugin = dumb transport** — no DB access. In-memory push for send, Core handles persistence via event bus.
5. **UnblockResolver abstraction** — single Core component that any source feeds into to unblock tasks. Replaces source-specific unblock paths. `tryUnblock({ by: "external_ref" | "task_id" })`.
6. **Dashboard API calls Daemon HTTP endpoint** — separate process can't instantiate UnblockResolver directly. Daemon exposes endpoint, dashboard proxies to it.
